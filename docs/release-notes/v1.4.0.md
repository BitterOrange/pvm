## Highlights

- **QEMU from two sources, chosen with `pvm qemu`.** pvm no longer packs QEMU itself. A VM runs either on a project build, which the new [pvm-qemu](https://github.com/BitterOrange/pvm-qemu) project compiles in CI from the signed upstream QEMU tarball and publishes with its complete source, or on your platform's official QEMU: Homebrew on macOS, your distribution's packages on Linux, and MSYS2 UCRT64 on Windows, which qemu.org links to.
  - `pvm qemu ls|install|use|check|rm|gc` manages them. Builds sit side by side under `~/.pvm/runtime/qemu/builds`, one is the default, and `pvm qemu use` switches it.
  - A project build is installed only when the archive's SHA-256 matches a digest pinned in this release, which CI checked against pvm-qemu's attestation. No `gh` or administrator rights are needed, and `pvm qemu install --file` works offline. A tag this release does not pin needs `--unpinned` and `gh`.
  - pvm runs QEMU only from the selected build, never from PATH or `/usr/local`. Every build passes a minimum version (8.2.0 on Linux, 11.1.0 elsewhere), accelerator and device probes, a test start with pvm's own arguments and a firmware check, and on macOS the hypervisor entitlement, before first use and whenever its binary changes. A project build whose files changed is refused.
  - Downloads resume and honour `HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY` and, on Windows, the static system proxy.
  - This release pins `11.1.3-pvm1` (QEMU 11.1.3) for macOS on arm64, Linux on amd64 and Windows on amd64. The QEMU version changes for every host: v1.3.6 shipped Homebrew's QEMU on macOS, Ubuntu's on Linux and a repack of an 11.1.0 build on Windows.
- **The daemon runs without QEMU.** `pvm ls`, `rm`, `snapshot rm`, exits and routes work; creating, starting, cloning, compacting, resizing and mounting say what to run. Clusters that cannot recover for want of QEMU are reported as blocked and stay cut off. `pvm qemu install` and `use` take effect within seconds, without a daemon restart, and `pvm daemon status` shows the build in use or why there is none.
- **PVM Desktop sets up QEMU.** Until a build is the default, the app shows a QEMU page with the pvm-qemu build (Install, Install from file) and QEMU from MSYS2 UCRT64. The WSL2 page can set up native QEMU too. Settings lists the builds, and About shows the one in use.
- **The gateway boots on M1 Macs.** An M1's hypervisor gives a guest a 36-bit address space, where QEMU's `virt` machine holds only 16 PCI buses, and the gateway's 64 root ports left it in the UEFI shell, so no VM could be created. The gateway now gets 15 root ports on such hosts, a cluster there holds at most 15 VMs and refuses the 16th with that reason, and a gateway's UEFI variables are reset at each cold start, which repairs gateways stuck in the shell.
- **No RAM snapshots under WHPX, said at once.** QEMU blocks migration of every WHPX VM, so `pvm snapshot create` on native Windows now refuses up front and points to the WSL2 backend.
- **RAM snapshots are bound to their QEMU.** A snapshot restores only into the build (its id and the SHA-256 of `qemu-system`) and CPU arguments that wrote it, and pvm refuses to snapshot a VM whose QEMU changed since it started.
- **`pvm doctor`** gains `qemu`, `qemu_builds`, `qemu_update` and `qemu_leftovers` checks, and `qemu_desktop` on Windows.

## Upgrading

- **The QEMU you have is taken over when it is a pinned build.** v1.4.x releases carry the pinned archives under the names v1.3.x upgrades from, with their source, so a v1.3.x `pvm upgrade` installs the pinned build in the old folder, and the v1.4.0 daemon moves it into `runtime/qemu/builds` at its first start after checking every file. The Windows installers do the same. Any other QEMU folder an older pvm left is not touched; `pvm qemu ls` lists it and `pvm qemu gc` removes it.
- **Restore RAM snapshots before upgrading.** Snapshots written before v1.4.0 record no QEMU build and are refused. To keep one, roll back (`pvm upgrade --rollback -y`), start the VM there, and upgrade again; or remove it with `pvm snapshot rm <vm>`. The first v1.4.0 command lists affected VMs once.
- **`pvm upgrade` no longer touches QEMU.** It checks that the new version accepts your default build, and never switches builds; `PVM_SKIP_QEMU` is gone. After `--no-restart`, run `pvm daemon restart`. `--rollback` to a v1.3.x recovery point also puts back that version's QEMU folder. `--to` refuses versions below v1.4.0; use `--rollback`, or that version's installer.
- **Windows: rerun the installer to get the new PVM Desktop.** `pvm upgrade` replaces only `pvm.exe`, and a PVM Desktop from before v1.4.0 cannot set up QEMU; pvm says so once. The MSI now installs its QEMU into `runtime\qemu\msi-payload\x86_64`.
- **Windows: the `.exe` and MSI installers no longer install over each other.** Both use the same folder, so mixing them left two entries in Apps and removing either broke the other. Uninstall one before switching to the other; VMs are kept.
- **Official QEMU.** To use it instead: `brew install qemu`, your distribution's packages (`sudo apt install qemu-system-x86 qemu-utils`), or `pacman -S mingw-w64-ucrt-x86_64-qemu` in an MSYS2 UCRT64 shell, then `pvm qemu use official`. A package manager upgrade of it makes older RAM snapshots unrestorable.
- **The bridge assets are in v1.4.x only.** v1.5.0 removes them and the takeover, so upgrade from v1.3.x through a v1.4.x release.

## Known issues

- No QEMU for Windows has virtio-9p, the pvm-qemu build included; host folders are mounted in WSL2 mode, or through workspaces.
- The v1.3.6 to v1.4.0 MSI upgrade with the payload in its new folder has not yet been tested on clean Windows snapshots.
- WHPX VMs still have no AVX.

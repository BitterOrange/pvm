# Roadmap

Planned work for the next release of this fork. Items move to the release notes once they ship; tick them in the Roadmap lists of README.md and README.zh-CN.md in the same release.

## Planned

- **The name: Proxied Virtual Machine (PVM).** The command and the project stay `pvm`; the abbreviation gets a meaning that says what sets it apart: a VM whose traffic leaves only through the exit you choose. Proposed form: "Proxied Virtual Machine (PVM)", without "The"; to be agreed with the upstream owner. Once agreed, the first sentence names it and states the fail-closed exit, so it does not read as a VM with an HTTP proxy set, for example "PVM (Proxied Virtual Machine) runs isolated VMs whose traffic leaves only through the exit you choose, and stops when that exit is down." It goes in README.md and README.zh-CN.md, SKILL.md and `pvm skill` together, the first line of `pvm --help`, and the installers' product description, with PVM Desktop's About text optional. Nothing is renamed: not the binaries, the module path, `~/.pvm` or the paths inside guests.

- **The rest of upstream.** `bab1221` and `31f41a8` are merged as of v1.3.1. Future upstream releases are pulled with `git merge upstream/master`; the history holds upstream's own squash commits, so it no longer conflicts.

- **`pvm exit-agent install|uninstall`.** Register the exit agent as a systemd service with one command, like `pvm daemon install` on the host. It writes `pvm-exit-agent.service` with the given `exit-agent` flags, refuses when another agent already holds the ports, keeps the existing token file and certificate so registered hosts need no re-enrollment, and runs `systemctl enable --now`. `uninstall` stops and removes the unit and leaves the token, certificate and registrations in place. Today the unit is written by hand; see [SKILL.md](../SKILL.md#standard-flow-deploy-an-exit-over-ssh).
- **`pvm app` beyond native Windows, and input method text in programs without ibus.** The host-to-guest clipboard bridge for macOS and Linux hosts, WSL2 support, and testing on macOS and Linux hosts. Input method text now goes in through an ibus engine in the Xpra server. The `xdotool` fallback, for programs without ibus and for text sent before the engine is registered, could lose a character from the first word and once showed stray characters; the cause was not found. Install the MSI end to end. See [docs/design/app.md](design/app.md#input-methods).
- **`pvm app`: input method candidates beyond Windows.** Since v1.3.4 the candidates of a host input method open at the app's text cursor on Windows hosts. Left: the macOS and Linux clients, which need their own way to place the input method's window, and a Chromium app's cursor moved without a click or a key, as by scrolling. See [docs/design/app.md](design/app.md#input-methods).

- **WHPX: AVX in VMs, and a QEMU per VM.** Today WHPX guests run on `host,-xsave` with `noxsave`, so they have no AVX, and a program that trusts CPUID still hits SIGILL on AVX instructions. Measured with the bundled QEMU 11.1 on a WHPX host, through pvm's own boot path: `host,-cet-ss,-cet-ibt` without `noxsave` gave AVX and AVX2 on 10 vCPUs and passed six minutes of `stress-ng --verify` (cpu, vecwide, vecmath, matrix, fp; 100 of 100), and plain `host` passed a shorter run; QEMU logs `failed to get xsave state`, cause unknown. It is not safe: in real use, a 10-vCPU VM on `host,-cet-ss,-cet-ibt` saw services and Claude Desktop crash after about 38 minutes, then systemd segfaulted and the guest kernel panicked; QEMU had logged the xsave error 18 times. The likely cause, not confirmed, is the WHPX backend failing to read a vCPU's XSAVE state and writing back stale register state. So VMs stay on `host,-xsave` with `noxsave` until a QEMU build syncs XSAVE with Hyper-V correctly; that build then needs a run of hours in real use, the guest kernel args removing `noxsave` as well as adding it, and the switch back for a QEMU without the fix. Alongside, several QEMU builds side by side (the bundled or own build, and the system's official one), chosen per VM in `vm.json`, with the CPU and irqchip arguments decided at start from that build's probed and declared capabilities instead of fixed in `Accel.Args()`; a RAM snapshot restores only into the same build and arguments.

- **Windows CI.** The `windows` job runs `go vet ./...` and the tests of the packages that pass on Windows, plus targeted `cli` tests such as the clipboard files and default VM. Left: the packages with failing tests, `daemon`, `exit`, `fsutil`, `gateway`, `gw/dns`, `image`, `keys`, `paths`, `qemu` and `vm`, mostly on permission bits, Unix paths and sockets. Each failing test is either fixed or skipped with the Unix-only reason, never excluded by whole package, and the package joins the list. On tags, install the freshly built `_setup.exe` silently on a Windows runner and check `pvm version`, that `pvm skill` matches SKILL.md, that the bundled `qemu-system-x86_64 --version` runs, that the bundled Xpra client passes pvm's 6.5.x check, and that uninstalling leaves nothing behind.

- **`pvm desktop` as a host window.** Open the VM's desktop the way `pvm app` opens a program: an Xpra window on the host instead of a noVNC page, with the same per-VM clipboard and drop settings and host input method text. Inside a workspace, the VM's file manager opens on the workspace folder. Needs a decision on running the XFCE session under Xpra's desktop mode next to the app display, and on what happens to `--public`, which only makes sense for the browser page.

- **PVM Desktop, the graphical app.** A window in the spirit of Docker Desktop for native Windows (WHPX), built with Wails and shipped in the Windows installers. Implemented: the core changes it needed in the CLI (a stored default VM, `pvm app` starting in the workspace folder, readiness in the VM list, the app catalog with `pvm app install`); the app itself, with the VM list (start, stop, delete, terminal, app, file manager), a create form with exit, app settings and preinstalled programs, exits and the default exit, workspaces with one-click terminal, app and file manager in the matching folder, the default VM and starting at login; the CI build; and the installers' file, Start menu shortcut and uninstall cleanup. Left:
  - The test from the installers on a native Windows host: install, uninstall, both login options and the WSL2 page. The app itself was run on a WHPX host from a local build; the list is in [docs/design/gui.md](design/gui.md#testing).
  - App settings that show what they hold. The dialog has eight settings, from the clipboard to the keyring, in a list that scrolls, and most people will not notice that more follow below its fold. A layout where every setting is in view, or plainly continues, for the dialog and the create form's app settings alike; to be designed with Claude Design.
  - Creating a workspace on a stopped VM fails, and the form is lost: the dialog closes on submit, and only the activity panel reports the failure, so every field has to be filled in again. The form should say before submitting that the VM is stopped and offer to start it, and a failed create should leave the dialog open with what was entered.
  - "Create PVM workspace" in the Explorer context menu, on the background of an open folder and on a folder itself. It opens PVM Desktop's create form with that folder as the host folder, in the running window when there is one. The installers write the entry under `HKCU\Software\Classes` (`Directory\Background\shell` and `Directory\shell`, no administrator rights) and remove it on uninstall. On Windows 11 a classic entry shows only under "Show more options"; the top-level menu needs an `IExplorerCommand` handler in a sparse package, to be decided.
  - `pvm upgrade` updates only `pvm.exe`; the app is updated by running the installer again.
  - A tray icon with VM state.
  - A daemon event stream in place of polling.
  - Screens for snapshots, port maps, mounts and logs.
  - The WSL2 backend, which today only gets an explanation page.
  - Exit lists with failover, a candidate below.
  - macOS and Linux builds.

## Candidates

Not yet scheduled.

- **`pvm ssh-config <vm>`.** Print an OpenSSH config entry for a VM, with its key, user and a `ProxyJump` through the gateway, so tools such as VS Code Remote-SSH, Mutagen and rsync can reach it by name. It prints only; pvm still never writes to `~/.ssh`.
- **Exit egress probe in `pvm exit test`.** The test only probes the agent itself, so it passes while a VPS firewall drops forwarded traffic. Add a probe that opens a connection to the internet through the tunnel.
- **A default image.** `pvm create --image ubuntu:26.04 --name dev2` repeats the same image on every create. `pvm image default ubuntu:26.04` records it, and `pvm create dev2` then needs only a name, given as a positional argument. With no default set and exactly one distro and version having a golden image, use that one; otherwise fail and list the choices. The create output names the image and golden version it used. The default lives in a host config file written with `fsutil.AtomicWrite`, and a default whose base and golden are gone is reported, not silently replaced.
- **Port maps without the gateway VM (optional).** Carry each map over the VM's `pvm.stream` channel instead of the gateway's QEMU user network, the way `pvm desktop` and `pvm app` already do. On native Windows this removes the 32-map limit, which comes from Windows QEMU polling at most 64 user-network sockets, and the roughly 12 MB/s ceiling of the gateway path. It needs datagram framing for UDP maps over the stream protocol, a decision on where guest-initiated maps (`pvm map` inside the VM) and clone `--inherit-ports` attach, and a migration that removes existing gateway forwards. The other fix for the limit is a Windows QEMU built with a larger `FD_SETSIZE`, which means maintaining our own QEMU build.
- **WHPX end-to-end tests.** Create, `pvm ssh`, workspace mount and `pvm app` on a real WHPX host. Hosted Windows runners are not expected to offer nested virtualization (to be confirmed), and TCG is too slow and misses WHPX-specific bugs, so this needs a self-hosted runner. As the repository is public, such a runner must only take manually dispatched runs, never pull requests.
- **Exit lists with failover.** A default exit list instead of one default exit: the first reachable exit carries a VM's traffic and the next takes over when it drops. Failover must keep the kill-switch fail-closed, so a VM with every exit down has no network, never the host's.
- **`pvm app`: fewer frames while the VM's windows are in the background. The maintainer leans against doing this.** Chromium draws in software in the VM, and on X11 that path takes its frame rate from the XRandR refresh rate of the window's monitor (`XrandrIntervalOnlyVSyncProvider`); Xpra's virtual monitor runs at 50 Hz. Measured in a 10-vCPU WHPX VM with an animated artifact preview open in Claude Desktop and nothing else happening, by switching the monitor to a mode of the same size at runtime: at 50 Hz about 21 frames a second, 2.85 cores in the VM and 4 on the host for QEMU; 30 Hz changed nothing, as the VM could not draw more than that anyway; 15 Hz gave 16 frames and 1.7 to 2.1 cores; 5 Hz gave 5 frames and about 0.6 cores. `xpra_start.py` could switch the monitor to about 5 Hz while none of the VM's windows has the host's focus, and back when one gets it. Left open: Xpra recreating the modes when the client's screen changes, and checking that GTK apps and Firefox do not redraw or lay out again on the switch.
- **Gateway rule drift false positive.** The gateway installs `to <server>/32 iif lo fwmark 0 lookup main`. `ip rule` omits a zero fwmark, so the drift check never matches and re-adds the rule every 10 seconds, logging `restored missing rule` each time.

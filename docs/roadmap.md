# Roadmap

Planned work for the next release of this fork. Items move to the release notes once they ship; the Roadmap sections of README.md and README.zh-CN.md list the next few in one line each and are updated in the same release.

## Planned

- **The name: Proxied Virtual Machine (PVM).** The command and the project stay `pvm`; the abbreviation gets a meaning that says what sets it apart: a VM whose traffic leaves only through the exit you choose. Proposed form: "Proxied Virtual Machine (PVM)", without "The"; to be agreed with the upstream owner. Once agreed, the first sentence names it and states the fail-closed exit, so it does not read as a VM with an HTTP proxy set, for example "PVM (Proxied Virtual Machine) runs isolated VMs whose traffic leaves only through the exit you choose, and stops when that exit is down." It goes in README.md and README.zh-CN.md, SKILL.md and `pvm skill` together, the first line of `pvm --help`, and the installers' product description, with PVM Desktop's About text optional. Nothing is renamed: not the binaries, the module path, `~/.pvm` or the paths inside guests.

- **`pvm app` beyond native Windows, and input method text in programs without ibus.** WSL2 support, and testing on macOS and Linux hosts, including the host-to-guest clipboard bridge that came with upstream v1.3.0-1.3.1 (merged in v1.4.1) and has not been run here yet. Input method text now goes in through an ibus engine in the Xpra server. The `xdotool` fallback, for programs without ibus and for text sent before the engine is registered, could lose a character from the first word and once showed stray characters; the cause was not found. Install the MSI end to end. See [docs/design/app.md](design/app.md#input-methods).
- **`pvm app`: input method candidates beyond Windows.** Since v1.3.4 the candidates of a host input method open at the app's text cursor on Windows hosts. Left: the macOS and Linux clients, which need their own way to place the input method's window, and a Chromium app's cursor moved without a click or a key, as by scrolling. See [docs/design/app.md](design/app.md#input-methods).

- **The upstream merge, tested end to end: v1.4.1.** v1.4.1 merges upstream v1.3.0-1.3.1. Its features have passed `go vet` and the unit tests only: Mihomo exits, `pvm check` and `require-check`, `pvm dashboard`, `pvm diag`, VMs started again after a daemon restart, the memory balloon, DoH failover and the clipboard bridge on macOS and Linux. Before the release they run on Windows (WHPX), Linux (KVM) and an M1 Mac, with a tunnel-loss test through a Mihomo exit.

- **QEMU outside the installers: v1.4.1.** v1.4.0 brought `pvm qemu` with its two sources, pvm-qemu builds pinned by digest and the platform's official QEMU (Homebrew, the distribution's packages, MSYS2 UCRT64 on Windows), a daemon that runs without QEMU, and the takeover of the QEMU that older versions installed; its Windows installers still carry the pinned build. Left: v1.4.1 drops QEMU from NSIS, the MSI and `pack-setup.sh`, and a new `install.sh` sets up QEMU with `pvm qemu install` (`PVM_QEMU=project|official|none`). The v1.4.0 MSI shipped with the `msi-payload` layout; the MSI experiment on clean Windows snapshots has not run. The bridge assets, the takeover and the Linux bridge for process records written before identities moved to `/proc` go in v1.5.0. See [docs/design/qemu.md](design/qemu.md).

- **Mihomo exits from a subscription link, and updates: v1.4.2.** Today `pvm exit import` takes only a config file, so a user downloads the subscription by hand and the nodes go stale when the provider changes them. Planned in two steps:
  - `pvm exit import my-exit --url` (the link also from stdin, so it stays out of shell history) and `pvm exit update my-exit`, which shows the nodes added and removed and the state of the selected node.
  - Then `--auto-update <interval>`, run by the daemon under the same rules, with each result in the audit log and the last update shown in PVM Desktop.

  The rules:
  - The link carries the subscription's token, so it is stored like a key (0600) and never printed in full: `diag`, logs, `exit ls` and PVM Desktop show only its host.
  - The host fetches it directly by default, so the provider sees the host's address; this is documented. The request uses a fixed client User-Agent that asks for the Clash/Mihomo format and does not name pvm.
  - An update never changes a VM's exit identity on its own: the selected node and the `--chain` nodes are kept by name, and when one of them is gone the exit fails closed with an explicit error instead of switching to another node.
  - A failed download or parse, or a result with no usable node, keeps the old config and reports the error. A new config goes through the same `proxyimport` sanitizing as a file and replaces the old one atomically.

- **`pvm-exit`, the exit server on its own: v1.4.1, then v1.5.0.** v1.4.1 brings `pvm-exit`, a server-only binary with a `config.yaml`, a system service run by the unprivileged `pvm-exit` user (kernel NAT with `CAP_NET_ADMIN` and `CAP_NET_RAW` only) or a systemd user service with no root, enroll and admin tokens, one-time invites, `pvm exit deploy` over SSH, `scripts/install-exit.sh` and a `.deb`, and `pvm-exit init --migrate` for `pvm exit-agent install` deployments. Tested in WSL (system, user and `.deb` installs, migration, kernel and userspace NAT, deploy as root, as a user and through a sudo password), on a Debian 12 VPS (deploy as root, then as a user whose sudo needs a password, invites, `pvm exit test`), and the arm64 build under QEMU user emulation with both NAT backends; CI installs the `.deb` on its amd64 and arm64 runners and joins it with an invite. Not yet tested: migrating a production `pvm exit-agent` VPS, and the release download path, which needs a published release. Left:
  - v1.5.0 removes `pvm exit-agent` and its install path; migrated VPSes are unaffected.
  - PVM Desktop's "add exit" form takes an invite as well as a token.
  - A short pairing code in place of the invite string, for when there is no SSH and no safe channel for a long string: a PAKE such as SPAKE2 or CPace binds a few words read aloud to the server's fingerprint, so a guessed code allows one attempt only. Needs a vetted Go implementation.
  - Homebrew for Linux, if asked for.

- **WHPX: AVX in VMs, and a QEMU per VM.** Today WHPX guests run on `host,-xsave` with `noxsave`, so they have no AVX, and a program that trusts CPUID still hits SIGILL on AVX instructions. Measured with the bundled QEMU 11.1 on a WHPX host, through pvm's own boot path: `host,-cet-ss,-cet-ibt` without `noxsave` gave AVX and AVX2 on 10 vCPUs and passed six minutes of `stress-ng --verify` (cpu, vecwide, vecmath, matrix, fp; 100 of 100), and plain `host` passed a shorter run; QEMU logs `failed to get xsave state`, cause unknown. It is not safe: in real use, a 10-vCPU VM on `host,-cet-ss,-cet-ibt` saw services and Claude Desktop crash after about 38 minutes, then systemd segfaulted and the guest kernel panicked; QEMU had logged the xsave error 18 times. The likely cause, not confirmed, is the WHPX backend failing to read a vCPU's XSAVE state and writing back stale register state. So VMs stay on `host,-xsave` with `noxsave` until a QEMU build syncs XSAVE with Hyper-V correctly; that build then needs a run of hours in real use, the guest kernel args removing `noxsave` as well as adding it, and the switch back for a QEMU without the fix. Alongside, the QEMU builds of the item above chosen per VM in `vm.json`, with the CPU and irqchip arguments decided at start from that build's probed and declared capabilities instead of fixed in `Accel.Args()`; a RAM snapshot restores only into the same build and arguments. This is phase 2 of [docs/design/qemu.md](design/qemu.md#phase-2-per-vm-qemu-and-whpx-avx), with QEMU 11.2.0 or a build with the three upstream WHPX fixes backported.

- **Windows CI.** The `windows` job runs `go vet ./...` and the tests of the packages that pass on Windows, plus targeted `cli` tests such as the clipboard files and default VM. Left: the packages with failing tests, `daemon`, `exit`, `fsutil`, `gateway`, `gw/dns`, `image`, `keys`, `paths`, `qemu` and `vm`, mostly on permission bits, Unix paths and sockets. Each failing test is either fixed or skipped with the Unix-only reason, never excluded by whole package, and the package joins the list. On tags, install the freshly built `_setup.exe` silently on a Windows runner and check `pvm version`, that `pvm skill` matches SKILL.md, that pvm takes the pinned pvm-qemu build over and `pvm qemu check` passes (from v1.4.1, after `pvm qemu install --file`), that the bundled Xpra client passes pvm's 6.5.x check, and that uninstalling leaves nothing behind. This runs on hosted runners; the QEMU work needs no self-hosted runner.

- **`pvm desktop` as a host window.** Open the VM's desktop the way `pvm app` opens a program: an Xpra window on the host instead of a noVNC page, with the same per-VM clipboard and drop settings and host input method text. Inside a workspace, the VM's file manager opens on the workspace folder. Needs a decision on running the XFCE session under Xpra's desktop mode next to the app display, and on what happens to `--public`, which only makes sense for the browser page.

- **PVM Desktop, the graphical app.** A window in the spirit of Docker Desktop for native Windows (WHPX), built with Wails and shipped in the Windows installers. Implemented: the core changes it needed in the CLI (a stored default VM, `pvm app` starting in the workspace folder, readiness in the VM list, the app catalog with `pvm app install`); the app itself, with the VM list (start, stop, delete, terminal, app, file manager), a create form with exit, app settings and preinstalled programs, exits and the default exit, workspaces with one-click terminal, app and file manager in the matching folder, the default VM and starting at login; the CI build; and the installers' file, Start menu shortcut and uninstall cleanup. Left:
  - The test from the installers on a native Windows host: install, uninstall, both login options and the WSL2 page. The app itself was run on a WHPX host from a local build; the list is in [docs/design/gui.md](design/gui.md#testing).
  - Creating a workspace on a stopped VM fails, and the form is lost: the dialog closes on submit, and only the activity panel reports the failure, so every field has to be filled in again. The form should say before submitting that the VM is stopped and offer to start it, and a failed create should leave the dialog open with what was entered.
  - "Create PVM workspace" in the Explorer context menu, on the background of an open folder and on a folder itself. It opens PVM Desktop's create form with that folder as the host folder, in the running window when there is one. The installers write the entry under `HKCU\Software\Classes` (`Directory\Background\shell` and `Directory\shell`, no administrator rights) and remove it on uninstall. On Windows 11 a classic entry shows only under "Show more options"; the top-level menu needs an `IExplorerCommand` handler in a sparse package, to be decided.
  - `pvm upgrade` updates only `pvm.exe`; the app is updated by running the installer again. See "PVM Desktop updates itself" below.
  - A tray icon with VM state.
  - A daemon event stream in place of polling.
  - Screens for snapshots, port maps, mounts and logs.
  - The WSL2 backend, which today only gets an explanation page.
  - Exit lists with failover, a candidate below.
  - macOS and Linux builds.

- **PVM Desktop updates itself.** PVM Desktop is the client and the pvm daemon the server, so they update separately. Desktop checks for a newer release, downloads the installer that matches how it was installed (the `_setup.exe` or the `_setup.msi`), verifies it the way pvm verifies its own releases (attestation and `SHA256SUMS`), and runs it. It can also run `pvm upgrade` for the local pvm, and later for a remote one (WSL2, another host). Until then `pvm upgrade` updates only `pvm.exe`, and the installer updates the app.

## Candidates

Not yet scheduled.

- **UDP port maps without the gateway VM (optional).** Since the upstream merge in v1.4.1, TCP maps of a running VM go over its `pvm.stream` channel. UDP maps still use the gateway's QEMU user network, which on native Windows limits the number of maps, because Windows QEMU polls at most 64 user-network sockets. Moving them needs datagram framing in the stream protocol, a decision on where guest-initiated maps (`pvm map` inside the VM) and clone `--inherit-ports` attach, and a migration that removes existing gateway forwards.
- **WHPX end-to-end tests.** Create, `pvm ssh`, workspace mount and `pvm app` on a real WHPX host. Hosted Windows runners are not expected to offer nested virtualization (to be confirmed), and TCG is too slow and misses WHPX-specific bugs, so this needs a self-hosted runner. As the repository is public, such a runner must only take manually dispatched runs, never pull requests.
- **Exit lists with failover.** A default exit list instead of one default exit: the first reachable exit carries a VM's traffic and the next takes over when it drops. Failover must keep the kill-switch fail-closed, so a VM with every exit down has no network, never the host's.
- **`pvm app`: fewer frames while the VM's windows are in the background. The maintainer leans against doing this.** Chromium draws in software in the VM, and on X11 that path takes its frame rate from the XRandR refresh rate of the window's monitor (`XrandrIntervalOnlyVSyncProvider`); Xpra's virtual monitor runs at 50 Hz. Measured in a 10-vCPU WHPX VM with an animated artifact preview open in Claude Desktop and nothing else happening, by switching the monitor to a mode of the same size at runtime: at 50 Hz about 21 frames a second, 2.85 cores in the VM and 4 on the host for QEMU; 30 Hz changed nothing, as the VM could not draw more than that anyway; 15 Hz gave 16 frames and 1.7 to 2.1 cores; 5 Hz gave 5 frames and about 0.6 cores. `xpra_start.py` could switch the monitor to about 5 Hz while none of the VM's windows has the host's focus, and back when one gets it. Left open: Xpra recreating the modes when the client's screen changes, and checking that GTK apps and Firefox do not redraw or lay out again on the switch.
- **Gateway rule drift false positive.** The gateway installs `to <server>/32 iif lo fwmark 0 lookup main`. `ip rule` omits a zero fwmark, so the drift check never matches and re-adds the rule every 10 seconds, logging `restored missing rule` each time.
